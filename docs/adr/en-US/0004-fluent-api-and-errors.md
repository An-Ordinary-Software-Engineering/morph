# ADR-0004: Fluent API and error handling

- **Status:** Proposed
- **Date:** 2026-10-11

## Context

The project draws on Fluent Migrator's semantics, where migrations are declared through method chaining.
The current API already follows that principle, with its own vocabulary:

```go
migrator.CreateTable("user", func(t *table.CreateTableConstraint) *table.CreateTableConstraint {
    return t.
        Column("id", types.Integer{}).PrimaryKey().AutoIncrement().
        Column("name", types.VarChar{Length: 50}).NotNull()
}, table.Options{DropIfExists: true, Engine: "INNODB"})
```

It has four problems:

- **Out-of-order panic:** calling a modifier before `Column`, for example `t.NotNull()`, accesses `payload[-1]` and **panics**.
- **Loose package function:** `CreateTable` is a package function that returns a value. The runner has no way to collect the operations of an `Up`/`Down` without global state.
- **MySQL-bound default:** `Default(value string)` takes ready-made SQL (`"CURRENT_TIMESTAMP()"`).
- **MySQL-bound option:** `Options.Engine` is MySQL-specific ([ADR-0003](0003-declarations-and-generation.md)).

## Decision

1. **We will keep the `Column(name, type)` style.** The type is a database-neutral value from `pkg/types`, given together with the name.
   Modifiers follow, chained.

   | Modifier            | Meaning                                                           |
   | ------------------- | ----------------------------------------------------------------- |
   | `PrimaryKey()`      | Part of the primary key. Implies `NotNull()`.                     |
   | `AutoIncrement()`   | Value generated by the database (`AUTO_INCREMENT`, `IDENTITY`, `SERIAL`, depending on the provider). |
   | `NotNull()`         | Rejects `NULL`. Without it, the column accepts `NULL`.            |
   | `Unique()`          | Uniqueness constraint.                                            |
   | `Default(v)`        | `v` is `types.CurrentTimestamp` (or another database-computed value) or a `string`, `bool` or numeric literal. |

2. **Per-stage typing:** the table only offers `Column`. `Column` returns a column builder that offers the modifiers and the next `Column`.
   Calling a modifier before declaring a column becomes a **compile error**, and the panic goes away.
   For this reason, the blueprint returns nothing: `func(t *table.CreateTableConstraint)`.

3. **Operations through a `Migrator`:** `Up` and `Down` receive a `*migrator.Migrator` (re-exported as `*morph.Migrator`).
   It records operations in the order they are declared (`CreateTable`, `DropTable` and, later, `AlterTable`, `RenameTable`, `Execute`),
   and the runner reads them afterwards:

   ```go
   type Migration interface {
       Version() int64       // YYYYMMDDHHMMSS
       Up(m *Migrator)
       Down(m *Migrator)
   }
   ```

4. **Neutral options with per-provider extension:** `table.Options` keeps only neutral fields (`DropIfExists`).
   Database-specific options go into `Options.Provider`, a map whose keys use the provider as namespace ([ADR-0003](0003-declarations-and-generation.md)).

5. **Accumulated errors, never panic.** Builders store validation errors: empty name, duplicate column, invalid size,
   `AutoIncrement` on a non-integer column, unsupported `Default` type, etc. The runner returns them (`mph up`) before running any SQL,
   joined with `errors.Join`, the way `bufio.Scanner` does with `Err()`. Messages include the migration, the table and the column.

### Example (importing through the root)

```go
package migrations

import "github.com/An-Ordinary-Software-Engineering/morph"

type CreateUser struct{}

func (CreateUser) Version() int64 { return 20261011120000 }

func (CreateUser) Up(m *morph.Migrator) {
	m.CreateTable("user", func(t *morph.Table) {
		t.Column("id", morph.Integer{}).PrimaryKey().AutoIncrement().
			Column("name", morph.VarChar{Length: 50}).NotNull().
			Column("email", morph.VarChar{Length: 50}).NotNull().Unique().
			Column("created_on", morph.Timestamp{}).NotNull().Default(morph.CurrentTimestamp)
	}, morph.TableOptions{
		DropIfExists: true,
		Provider:     map[string]string{"mysql.engine": "INNODB"},
	})
}

func (CreateUser) Down(m *morph.Migrator) {
	m.DropTable("user")
}
```

## Alternatives considered

- **Fluent Migrator's literal vocabulary** (`WithColumn(name).AsString(50)`): the type sits in a separate stage from the name,
  and each type becomes a method. With `Column(name, type)`, the type is a value from `pkg/types`, and adding a new type does not change the builders' API.
- **Keep `CreateTable` as a package function and collect operations in a global registry:** creates global state, hinders testing and is not concurrency-safe.
- **Return `(builder, error)` from each call:** breaks chaining.
- **Internal `panic` + `recover`:** hides the error flow and feels foreign to Go users.

## Consequences

- Incompatible changes relative to the current API: the blueprint no longer returns a value, `CreateTable` becomes a `Migrator` method,
  `Default` no longer takes SQL, and `Engine` leaves `Options`. This is acceptable while the project is at `v0`.
- At the root, some names need a prefix to avoid collisions or ambiguity (`table.Options` → `morph.TableOptions`,
  `table.CreateTableConstraint` → `morph.Table`).
- Errors only show up when the runner validates, not at the exact call site. So messages must identify the migration, the table and the column.
